# 記録.txt — PDF掲示物共有PWA 開発ログ

## 2026-07-06

### プロンプト概要
ユーザーより「社内掲示物をスマホで簡単・安全に閲覧できるWebサービス」の新規開発依頼。
PDFアップロード→ページ毎にWebP画像へ変換→ランダムURL共有→パスワード保護→PWA対応→Push通知、という閲覧専用サービス。
技術構成: Next.js(App Router) + TypeScript + Tailwind CSS。アプリアイコンは提供されたPNG
(`ChatGPT Image 2026年7月6日 21_24_07.png`)を使用。

### 設計フェーズ
- Plan modeで事前設計を実施。ユーザーへの確認事項:
  1. DB/ストレージ構成 → 「ローカル完結・即実行可能(Prisma+SQLite、ローカルディスク)」を選択。
     将来Postgres/R2/Supabase Storageへ移行できる抽象化を必須要件として設計。
  2. 管理画面認証 → 「共有の管理者パスワード1つ」を選択(単一パスワード、bcryptjsハッシュ照合)。
  3. Push通知送信タイミング → 「管理画面の『通知送信』ボタンを押した時のみ」を選択(自動送信はしない)。
- Plan agentにPDF→画像変換パイプラインの技術調査を依頼。結論:
  `pdfjs-dist`(legacy build) + `@napi-rs/canvas`(Windows prebuiltバイナリで安定) + `sharp`(WebPエンコード)。
  DB: Prisma+SQLite、ID生成: nanoid(24)、セッション: jose(HS256)、PWA: @serwist/next、
  Push: web-push(VAPID)、期限切れ削除: node-cron(instrumentation.tsで起動時登録)。
- 最終プランをユーザー承認済み(保存先: `C:\Users\PC_User\.claude\plans\concurrent-launching-plum.md`)。

- **Step 2 完了(PDF→WebP変換パイプライン)**:
  - 調査の結果、最新の `pdfjs-dist`(v5.6.205)は `@napi-rs/canvas` をoptionalDependencyとして正式サポート済みと判明。
    独自の `NodeCanvasFactory` を書く必要はなく、`@napi-rs/canvas` の `createCanvas()` で生成したcanvasを
    `page.render({ canvas, canvasContext, viewport })` にそのまま渡すだけで動作。
  - さらに `@napi-rs/canvas` の `Canvas.toBuffer('image/webp', quality)` がネイティブWebPエンコードに対応していたため、
    **sharpは変換パイプラインからは不要と判断し外した**(sharpはStep9のPWAアイコン生成でのみ使用する予定)。
    これによりPNG中間生成→sharp再エンコードという二重圧縮を避け、依存も1つ減らせた。
  - ハマった点: `cMapUrl`/`standardFontDataUrl` にWindowsの `\` 区切りパスを渡すと
    `Invalid factory url: ... must include trailing slash` エラー。pdfjs内部ではURL文字列として扱われるため、
    OSに関わらず `/` 区切り+末尾スラッシュに正規化する `toFactoryUrl()` を実装して解決。
  - 動作確認: pdfkitで生成した3ページのテストPDF(28pt見出し〜9pt極小文字、罫線ボックス入り)を変換し、
    1600x2263pxのWebP(各29KB程度)を目視確認。9pt文字も潰れず可読。変換時間は3ページで約1.15秒。
  - 拡張子は`.pdf`だが中身がPDFでない偽ファイル("PK fake excel content..."というテキスト)を投入し、
    `assertValidPdfUpload` がマジックバイト不一致で正しく拒否することを確認。
  - `npx tsc --noEmit` / `npm run lint` ともにエラー無し。テスト用の一時スクリプト・出力は作業後に削除済み。

- **Step 5+6 完了(共有ページ閲覧 + パスワード保護/ロックアウト)**:
  - Step 5(閲覧画面)とStep 6(パスワード保護)は、既にDBスキーマ(`ShareLoginAttempt`)や
    `view-token.ts`がStep 3の時点で用意済みだったため、手戻りを避けるため同時に実装した。
  - `src/lib/share/lockout.ts`: `ShareLoginAttempt`テーブルを使ったDB永続化ロックアウトを実装。
    5回失敗で5分ロック、以降失敗ごとに倍化(最大24時間)する指数バックオフ方式。
    プロセス再起動をまたいで有効(インメモリのレート制限とは別に、こちらが本質的なブルートフォース対策)。
  - `src/lib/auth/session-secret.ts`に`getSessionSecretString()`を追加し、IPハッシュ化(`hashIp`)で
    SESSION_SECRETを生文字列として再利用できるようにした(既存の`getSessionSecretKey()`はこれをラップする形に整理)。
  - `src/lib/share/expiry.ts`に`isShareExpired()`を追加。`status`フィールド(cronによる非同期更新、Step7で実装予定)と
    `expiresAt`(即時判定)の両方をチェックすることで、cronが未実行の期限切れ共有にも即座にアクセスできないようにした。
  - API: `POST /api/share/[shareId]/verify`(パスワード検証、インメモリレート制限+DBロックアウトの二重防御、
    成功時にhttpOnly Cookie `view_token_{shareId}`を30日間有効で発行)、
    `GET /api/share/[shareId]/pages/[n]`(画像バイナリ配信、パスワード付き共有は Cookie 検証必須、
    `updatedAt`+ページ番号からETagを生成し304対応、Cache-Control: private, no-cache)。
  - UI: `/share/[shareId]`(サーバーコンポーネント。共有が存在しない/期限切れなら`notFound()`、
    パスワード必須かつ未認証ならパスワードフォーム、それ以外はビューアを表示)、
    `PasswordForm`(クライアント、検証成功で`window.location.reload()`)、
    `Viewer`(縦スクロールでページ一覧表示)、`ZoomableImage`(`react-zoom-pan-pinch`使用)。
  - **設計判断**: ピンチズーム/ダブルタップズームと「複数ページの縦スクロール」を両立させるため、
    各ページ画像を個別の`TransformWrapper`でラップし、`scale<=1`の間は`panning.disabled=true`にして
    一本指の縦ドラッグをページの通常スクロールに委ねる方式を採用。ピンチ(2本指)とダブルタップは
    scaleに関わらず常に有効なため、ズームイン操作自体は妨げられない。`onTransform`コールバックで
    scaleを監視し、1.01を超えたら`zoomed=true`にしてpanningを有効化する。
  - **ハマった点**: `react-zoom-pan-pinch`の型定義で、`onTransform`コールバックの第2引数は
    `ReactZoomPanPinchState`(`previousScale`等を含むフル状態)ではなく、
    `{ scale, positionX, positionY }`という簡略型だった。ライブラリの型エクスポート名と実際のコールバック
    シグネチャが一致していなかったため、tscのエラーメッセージを頼りに実際の型に合わせて修正。
  - next/imageではなく生の`<img>`を使用(ズームライブラリがDOM参照を直接操作するため)。
    ESLintの`no-img-element`警告は理由をコメントで明記した上で該当行のみ無効化。
  - 動作確認(一時スクリプト`scripts/test-create-share.ts`でPDF変換を経由せず、sharpでダミー画像の
    共有を2件作成→curlで一連のAPIを検証→確認後スクリプトとテストデータは削除):
    - パスワードなし共有: `/share/{id}`が200でビューアを直接表示、画像APIも200。
    - パスワードあり共有: `/share/{id}`はパスワードフォームを表示(200)、認証前の画像APIは401。
    - 誤パスワードは401、正パスワードは200+Set-Cookie、Cookie付きの画像取得は200。
    - ETagを使った再検証で304が返ることを確認。
    - 別の共有で誤パスワードを6回連続送信→5回目の失敗でロック、6回目以降は正しいパスワードでも429。
    - 存在しない共有IDへのアクセスは404(カスタムnot-foundページ)。
  - `npx tsc --noEmit` / `npm run lint` ともにエラー無し(imgタグの警告のみ、理由を明記して意図的に許容)。

    cronが5分間隔で走るまでの間も期限切れ共有への閲覧は防がれる(cronは実体の削除・クリーンアップ専任)。
  - 動作確認: 一時スクリプトで「期限を1時間過去に設定した共有」と「1時間後が期限の共有」を作成し、
    `cleanupExpiredShares()`を直接実行 → 期限切れの共有のみDBレコード・ストレージファイルとも削除され、

    確認後、一時スクリプトと有効な方のテストデータは削除済み。

  - `scripts/generate-icons.ts`: 提供PNG(`ChatGPT Image 2026年7月6日 21_24_07.png`、1254x1254・不透明)から
    `sharp`でicon-192/icon-512/icon-maskable-512(セーフゾーン確保のため80%に縮小し中央配置)/

    (next buildで自動生成されるsw.jsとは異なり)git管理下に置く。
  - **設計判断**: iOSのapple-touch-startup-imageは「CSS論理px × デバイスピクセル比」の組み合わせでしか
    マッチしないため、実ピクセルサイズだけでなく機種ごとのCSS論理サイズ・DPRも
    `src/lib/pwa/splash-screens.ts`に一元管理する共有設定として切り出した。
    `generate-icons.ts`(画像生成)と`layout.tsx`(`<link rel="apple-touch-startup-image">`生成)の

  - `src/app/manifest.ts`(Next.js標準の動的manifestファイル規約)でmanifest.webmanifestを生成。
  - `src/app/sw.ts`: `defaultCache`(Next.js向けのHTML=NetworkFirst/静的アセット=CacheFirst相当の推奨設定)に加え、
    共有ページの画像(`/api/share/*/pages/*`)には独自のStaleWhileRevalidateルールを先頭に追加し、
    「オフライン時も最後に見た画像を表示する」要件を満たした。
  - `src/app/layout.tsx`: manifestは自動リンクされるため、apple-touch-icon/apple-mobile-web-app-*系メタタグ・
    theme-color(`viewport`エクスポート)・スプラッシュ`<link>`一式を追加。
  - `src/components/share/install-prompt-button.tsx`: `beforeinstallprompt`をハンドリングし、
    Android/Chrome等の対応環境でのみ「ホーム画面に追加」ボタンを表示(iOS Safariは同イベント非対応のため
    非表示のまま、共有シートからの手動追加に委ねる)。共有ビューア画面に配置。
  - **ハマった点1**: `sw.ts`はNode.js用ではなくService Worker用のグローバル型(`ServiceWorkerGlobalScope`等)
    が必要だが、`/// <reference lib="webworker" />`をファイル先頭に足すと、プロジェクト全体のtscプログラムに
    dom libとwebworker libが同時に読み込まれてグローバル型が衝突し、無関係な多数のクライアントコンポーネントで
    `window`/`document`が見つからないエラーが大量発生した。最終的に、`sw.ts`自体には
    `/// <reference lib="webworker" />` + `/// <reference no-default-lib="true" />`を残しつつ、
    ルートの`tsconfig.json`の`exclude`に`src/app/sw.ts`を追加し、アプリ本体のtscプログラムから
    完全に切り離すことで解決(Next.js/webpackのビルド自体はtsconfig.jsonのexclude設定と無関係にファイルを
    処理するため、実際のビルドには影響しない)。
  - **ハマった点2**: このプロジェクトはNext.js 16のデフォルトであるTurbopackを使用していたが、
    `@serwist/next`は内部でwebpack専用のInjectManifestプラグインを利用しており、Turbopackとは非互換
    (「webpack configとTurbopack configの両方は使えない」エラーでビルド自体が失敗)。

### 実運用開始後に発覚した不具合対応(2026-07-07)

ユーザーが実際に管理者パスワードを設定して`npm run dev`で使い始めたところ、Step 11のCSP導入時の
検証(本番ビルド`npm run start`でのみ実施)では気づけなかった、開発モード(`npm run dev`)特有の
不具合が2件発覚した。

- **不具合1: ログインボタンが押せない(実際は画面全体が無反応)**:
  ユーザーからブラウザのConsoleスクリーンショットの共有を受け、原因を特定。
  `Uncaught EvalError: ... 'unsafe-eval' is not an allowed source of script`が
  `next/dist/compiled/@next/react-refresh-utils/dist/runtime.js`から発生していた。
  Next.jsの開発時Fast Refresh(コード変更のホットリロード)は内部で`eval()`を使うため、
  Step11で追加したCSPの`script-src`に`'unsafe-eval'`が無いと**開発モードのJS実行が丸ごと止まる**
  (ボタンが押せないどころか、あらゆるクライアント側の動作が停止する)。本番ビルドでは
  Fast Refreshが存在しないため元々問題なかったが、本番ビルドでしか検証していなかったため
  この開発モード特有の不具合を見逃していた。`src/proxy.ts`の`buildCsp()`で
  `process.env.NODE_ENV === "production"`のときのみ`'unsafe-eval'`を外し、開発時は許可する形に修正。

- **不具合2: PDFアップロードが500エラーで失敗**:
  ユーザーから実際のアップロードエラーのスクリーンショット(`POST /api/admin/shares 500`)の共有を受け、
  開発サーバーのログで`TypeError: Object.defineProperty called on non-object`
  (`src/lib/pdf/convert.ts:48`、`await import("pdfjs-dist/legacy/build/pdf.mjs")`の行)を確認。
  原因はStep9で`next dev`/`next build`をTurbopackからwebpackへ切り替えて以降、
  `pdfjs-dist`が`next.config.ts`の`serverExternalPackages`に含まれておらず、webpackが
  bundleしようとしていたこと。`pdfjs-dist`のlegacyビルドは`globalThis`への独自polyfillパッチを
  素のESM実行前提で行っており、webpackでバンドルされると(`@napi-rs/canvas`のネイティブバイナリと
  同様に)内部の`Object.defineProperty`呼び出しが対象を見失い実行時エラーになっていたと判明。
  `next.config.ts`の`serverExternalPackages`に`"pdfjs-dist"`を追加し解決。
  **重要な教訓**: Step9でTurbopack→webpackへの切替を行って以降、実際のPDFアップロード
  (pdfjs-distを経由する本物の変換パイプライン)を一度も再検証していなかった
  (Step4以降の検証はすべて`storage.put`で直接WebPを書き込むバイパス方式を使っており、
  本物のPDF→WebP変換ルートを一切通していなかった)。ビルドツールを切り替えるような変更の後は、
  ショートカットで検証していた経路についても実際のエンドツーエンドフローを一度は通す必要がある。

### 不具合修正: 実際のWord印刷PDFでアップロードが失敗する(2026-07-07)

ユーザーから「またアップロードに失敗します」と報告。ブラウザのエラースタックだけでは
原因特定に至らず、実際に失敗したPDFファイルの場所を聞いたところ
`C:\Users\PC_User\Pictures\Screenshots\text.pdf`(Word印刷で作成)と判明。
このファイルを直接`convertPdfToWebpPages`にかけて再現に成功した。

- **エラー内容**: `Error: Value is none of these types \`String\`, \`Path\`,`(`code: 'InvalidArg'`)が
  pdfjs-distの`CanvasGraphics.paintChar`(`ctx.fill(path)`)で発生。
- **原因調査**: pdfjs-dist(legacyビルド)はNode環境で動作する際、`globalThis.Path2D`/
  `DOMMatrix`/`ImageData`が未設定なら`@napi-rs/canvas`から自動でポリフィルする処理を持つ
  (`pdf.mjs`内、`createRequire(import.meta.url)`経由の内部require)。ところがこの内部requireが、
  このアプリの`src/lib/pdf/convert.ts`が`import`している`@napi-rs/canvas`とは**別インスタンス**を
  読み込んでしまうことがあり(実際に`globalThis.Path2D !== 自分がimportしたPath2D`であることを
  診断スクリプトで確認)、埋め込みフォント(Word/Excel印刷PDFで一般的)のグリフを
  Path2Dベースで描画する際、pdfjs側が生成したPath2Dインスタンスと、こちらが
  `createCanvas()`したcontextのネイティブ実装が別クラス扱いになり、N-APIの型チェックで
  弾かれていた。標準14フォント(pdfkitのデフォルト等)はネイティブ`fillText`の別経路を通るため
  この問題を踏まず、これまでの一時的な動作確認(Step2、Step10〜12の各確認)ではたまたま
  再現しなかった。
- **修正**: `src/lib/pdf/convert.ts`の先頭で、pdfjs-distをdynamic importする前に
  自分がimportした`Path2D`/`DOMMatrix`/`ImageData`を`globalThis`へ`??=`で先回り設定するように
  変更。pdfjs-dist側のポリフィルは「まだ設定されていなければ」のみ行うため、
  常にこちらのインスタンスが使われるようになる。
  **ハマった点**: 修正を`npm run dev`のプロセスに反映させた直後も失敗が再現した。
  原因は、修正前のコードで実行された過去の失敗リクエストによって、その時点の
  (誤った別インスタンスの)`globalThis.Path2D`が**プロセスの生存期間中ずっと**設定されたままに
  なっており、`??=`ガードのため修正後のコードもそれを見て「既に設定済み」と判断し
  上書きしなかったため。devサーバーを再起動(=プロセスを作り直す)ことで解決した。
  今後同様の「globalThis状態の汚染」が疑われる場合は、コード修正後の一度のリクエストだけでなく
  プロセスの再起動有無も確認すること。
- 動作確認: 実際に失敗した`text.pdf`を直接`convertPdfToWebpPages`にかけて成功を確認、
  出力画像を目視して日本語embeddedフォントのテキストが正しく描画されていることを確認。
  さらに開発サーバー再起動後、実際の管理者APIへ本物のmultipartアップロードとして
  同じファイルを送信し、201で共有が作成され配信された画像も正しいことを確認。
  `npm run build`(本番ビルド)も問題なく成功することを確認。
  `npx tsc --noEmit` / `npm run lint` ともにエラー無し。確認用の共有・一時スクリプトは
  作業後にすべて削除済み(`text.pdf`自体はユーザー作成のテストファイルのため削除せず残した)。

### 不具合対応: 選択画面のPDF/画像編集入口へのUI改善・AIインペインティングの品質改善(2026-07-07)

ユーザーから2点の要望。(1)AIインペインティングを実際に使ってみたところ、塗った範囲だけでなく
ページ全体の文字が激しく歪んでしまう。(2)編集画面に「1つ前に戻る」「1つ先に進む」ボタンを追加してほしい。

- **戻る/進むボタン**: `pdf-editor.tsx`に`history`/`future`という2つのスタック(state)を追加。
  各ツール(トリミング・拡大縮小・形式変換・AIで消す)のonApply実行前に現在の`pages`を
  `history`へ積み、`future`をクリアする。「1つ前に戻る」で`history`の末尾を`pages`に戻しつつ
  現在の状態を`future`へ積む(逆が「1つ先に進む」)。ボタンはツールタブ(トリミング等)と
  同じ行の先頭に配置(初回はタブの上に別行で置いたが、ユーザー指示で同じ行に統合)。
- **AIインペインティングの歪み(1回目の対処、不十分だった)**: gpt-image-1の出力解像度が
  1024x1024等の固定3種類しか無く、元画像の縦横比と一致しないため、`sharp`の`resize(fit:"fill")`
  (縦横比を無視した引き伸ばし)で元サイズに戻す際にページ全体の文字が歪んでいた。まず
  (a)元画像に近い縦横比の出力サイズを選ぶ、(b)引き伸ばしではなく`fit:"cover"`(縦横比を保って
  拡大縮小+中央トリミング)に変更、を試したが、ユーザーからは「全然だめ、全体がすごく歪む」と
  改善が確認できなかった。
- **AIインペインティングの歪み(2回目の対処、根本原因の特定)**: 原因は「ページ全体を毎回AIに
  渡していること」自体にあると判断。生成系画像モデルは画像全体を一度エンコード・デコードする
  ため、たとえ縦横比を合わせても、その往復で全体(特に細かい文字)の画質が劣化する。対処として、
  塗った範囲(ブラシストロークの外接矩形)の周囲に文脈用の余白を持たせた正方形だけを切り出して
  AIに渡し、返ってきた結果を元のページ画像(無加工)の上にその位置だけ貼り戻す方式に変更
  (`inpaint-tool.tsx`に`boundsRef`でブラシの外接矩形を追跡する処理を追加、
  `CROP_PADDING_FACTOR`/`MIN_CROP_SIZE`定数で余白・下限サイズを調整)。これにより、
  塗っていない部分はAIを一切経由せず完全に無加工のまま残るはずだった。
- **AIバックエンドの入れ替え(ユーザー判断)**: 上記のクロップ方式に修正した上でも
  ユーザーからは改善が見られないとの報告があり、「LaMaというものはどうですか」と提案を受けた。
  AskUserQuestionで導入方法を確認したところ、「Replicate経由でLaMaを使う」を選択
  (自前サーバー不要・従量課金・Python環境構築が不要なため)。OpenAIの`gpt-image-1`画像編集API
  (テキストプロンプトで指示する汎用画像生成モデル)を、Replicateでホストされている
  `allenhooo/lama`(LaMa: Resolution-robust Large Mask Inpainting with Fourier Convolutions、
  テキストプロンプト不要の専用インペインティングモデル)に完全に置き換えた。
  - 依存関係: `openai`パッケージを削除し、`replicate`パッケージを追加。
  - 環境変数: `OPENAI_API_KEY`を削除し、`REPLICATE_API_TOKEN`(必須)・
    `REPLICATE_LAMA_MODEL`(任意、既定値`allenhooo/lama`)を`.env`/`.env.example`に追加。
  - `src/app/api/admin/edit/inpaint/route.ts`を全面書き換え。LaMaのマスク仕様は
    「白=修復対象、黒=保持」という濃淡グレースケール画像であり、このアプリのマスクcanvas
    (「不透明=保持、透明=修復対象」というアルファチャンネル方式、元々OpenAIのマスク仕様向けに
    設計)とは方式が異なるため、`sharp`でアルファチャンネルを抽出(`extractChannel("alpha")`)
    して反転(`negate()`)し、グレースケールマスクに変換してから渡す変換ステップを追加した
    (クライアント側のcanvas描画ロジックは一切変更していない)。LaMaは「resolution-robust」を
    謳っており基本的に入力と同じ解像度で結果を返すため、以前のような固定サイズへの強制リサイズは
    不要になったが、念のためサイズが異なる場合のみ`fit:"cover"`でリサイズするフォールバックを残した。
  - Replicateの公式Node SDK(`replicate`パッケージ)の`replicate.run()`はモデルによって
    出力が「URL文字列」「FileOutput(blob()/url()を持つReadableStream)」のいずれの形でも
    返り得るため、両方に対応する`extractOutputBuffer()`ヘルパーを実装した。
  - UIは指示通り一切変更していない(`inpaint-tool.tsx`のブラシ描画・クロップ&貼り戻しロジックは
    そのまま、バックエンドのAPI呼び出し先だけを差し替えた)。
  - `npx tsc --noEmit` / `npm run lint` / `npm run build`いずれもエラー無しを確認。
    実際のReplicate呼び出し自体は`REPLICATE_API_TOKEN`をユーザーが取得・設定した後に
    実機で確認予定(取得方法をREADME.mdの環境変数テーブルに追記済み)。

### 実機確認: Replicate/LaMa連携の動作確認とハマった点(2026-07-07)

ユーザーがReplicateアカウントを作成し`REPLICATE_API_TOKEN`を設定。実際にAPIを呼び出して
段階的に3つの問題を解決し、最終的に動作確認まで完了した。

- **1回目のエラー(404 Not Found)**: `allenhooo/lama`をowner/name形式のみで呼び出すと
  `https://api.replicate.com/v1/models/allenhooo/lama/predictions`が404を返した。
  このモデルは「公式モデル」化されておらず、owner/nameだけでは解決できないことが判明。
  Replicateの`/allenhooo/lama/versions`ページ(WebFetchはJS描画のため内容を拾えず、
  `curl`で生HTMLを取得し`grep -oE "[0-9a-f]{64}"`で正確な64文字のバージョンハッシュを抽出)
  から最新バージョン`cdac78a1bec5b23c07fd29692fb70baa513ea403a39e643c48ec5edadb15fe72`を特定し、
  `"allenhooo/lama:{version}"`という形式(バージョン固定)に変更して解決。
  **教訓**: 長い16進数のハッシュ文字列をLLM経由のWebFetchで抽出すると誤りが混入するリスクが
  あるため、正確性が必要な場合は`curl`+`grep`で生データから直接抽出する方が安全。
- **2回目のエラー(402 Payment Required・insufficient credit)**: モデル解決自体は成功したが、
  Replicateアカウントにクレジットが無く実行できず。ユーザーがBilling画面で
  オートリロードのチェックボックスだけオンにして金額欄を空欄のまま保存しており、
  実際にはクレジットが購入されていなかった。「When credit balance goes below」に$5、
  「Reload credit balance to」に$15(いずれも最低額)を入力して保存することで、
  残高が閾値以下だったため即座に$15分課金され、数分後に反映された。
- **動作確認**: 白背景に黒い四角(消したい物体を模した合成画像)+その四角部分だけを

scaleX/scaleYを計算するように変更。Playwrightで縮小表示が発生する条件(ビューポート幅500px、
画像は1446x551px)を再現し、表示領域の25%〜75%(50%×50%)をドラッグ選択→適用した結果が

  結合後PDFの実ページ数を保存する。差し替え(PATCH)時は、PDF↔ラスタのモード切り替えも含め、

【2026-07-08】PWAでログイン時にアプリの外(Safari)に遷移してしまう不具合の修正

ユーザーより「PWA(ホーム画面に追加したアプリ)でログインすると別のページに遷移してしまい、
アプリの画面ではなくなる」と報告。実機(iPhone)のスクリーンショットでも、上部に「完了」ボタンと

- **原因**: `src/app/manifest.ts`の`start_url`は`/collection/{GALLERY_PATH}`(閲覧者向けギャラリー)だが、
  `scope`が未設定だった。Web App Manifestの仕様では`scope`省略時、デフォルトのスコープは
  `start_url`の**ディレクトリ**(`/collection/`)になる。一方、管理者ログイン画面は
  `src/app/a/[token]/page.tsx`という別ディレクトリ(`/a/`)配下にある。iOSのホーム画面アプリ

  仕様であるため、ログイン時にアプリから抜ける現象が発生していた。
- **修正**: `src/app/manifest.ts`に`scope: "/"`を追加し、オリジン全体をPWAの適用範囲に広げた。
  これにより`/a/[token]`(ログイン)や`/a/[token]/admin`(管理画面)への遷移もstandalone表示のまま
  維持されるようになる。
- 検証: `npx tsc --noEmit`でエラー無し。ユーザーの承認を得てコミット・push実施
  (コミット4ac6ccc、`main`ブランチ、GitHub経由でVercelへ自動デプロイ)。
- **ユーザーへの申し送り事項**: iOSは一度ホーム画面に追加したPWAのmanifest情報をインストール時に
  キャッシュするため、デプロイが反映されても既存のホーム画面アイコンには自動反映されない。
  動作確認の際は、ホーム画面のアイコンを一度削除し、Safariで開き直してから
  「ホーム画面に追加」をやり直す必要がある旨を伝えた。

前回の`overscroll-behavior: none`だけではiPhoneのホーム画面PWA(standalone)で
スワイプ戻るを防ぎきれないとの報告。あわせて2件。(1)「描画やAIモードだと、二本指で拡大、

【2026-07-09】スワイプ戻る対策の追加強化(JS側でのpreventDefault)

前回のtouch-action: pan-y pinch-zoom(CSS)だけでは対策しきれておらず、iPhoneの
ホーム画面PWA(standalone)で「アプリ全体で常に」スワイプ戻るが再現するとの報告。
AskUserQuestionで再現環境を確認したところ、ホーム画面追加のstandalone PWAでのみ
発生(Safariブラウザタブでは未確認)。

- **原因**: iOSのWKWebViewベースのstandalone PWAでは、画面端からのスワイプ戻る
  ジェスチャーがCSSのtouch-actionだけでは完全に抑止できない端末・OSバージョンが
  あることが知られている(ジェスチャー認識自体がタッチ開始直後に決定されるため、
  CSSの制約が間に合わない/優先されないケースがある)。
- **対策**: `src/components/edge-swipe-guard.tsx`を新規作成し、`document`に
  `touchstart`を`{ passive: false }`で登録。タッチ開始位置が画面左右端から20px
  以内かつ1本指の場合のみ`preventDefault()`を呼び、ジェスチャー自体の発火を
  未然に止める。2本指以上(ピンチズーム操作)は対象外とし、既に横スクロールを
  個別許可している要素(PDF編集のサムネイル一覧)は`data-pan-x`属性を目印にして
  ガードの対象外にした(`pdf-editor.tsx`の該当divに`data-pan-x`を追加)。
  `src/app/layout.tsx`のbody直下にマウントし、アプリ全体に適用。
- 検証: `npx tsc --noEmit` / `npm run lint` ともにエラー無し。一時的にPlaywrightを
  再導入し、タッチ対応コンテキスト(`hasTouch: true`)の実ページで本物の`TouchEvent`/
  `Touch`を5パターン(左端1本指→prevent される、画面中央→されない、左端だが
  `data-pan-x`要素上→されない、左端+2本指→されない、右端1本指→prevent される)
  発火させ、全て期待通りの`defaultPrevented`挙動になることを確認。確認後、
  一時スクリプトは削除・Playwrightはアンインストール済み(package-lock.jsonの
  差分も元に戻した)。開発サーバーは起動していない。実機での最終確認(それでも
  直らない場合はさらに強い対策が必要)はユーザーに依頼する。

【2026-07-09】スワイプ戻る対策の第3段(履歴レベルでの無効化)

JS(touchstart)対策後も実機で改めて確認したところ「直らない」との報告。AskUserQuestionで
実際の挙動を確認すると、アプリ内の前の画面へ実際に遷移してしまうとのこと(見た目だけの
アニメーションではなく、本当にNext.jsのルーティングが前のページへ戻っていた)。

- **原因の再整理**: iOSのWKWebViewベースのstandalone PWAでは、画面端スワイプ戻る
  ジェスチャーがDOMのタッチイベントより手前(ネイティブのジェスチャー認識レベル)で
  確定してしまう端末があり、CSSのtouch-actionもJSのtouchstart側でのpreventDefault
  も、ジェスチャー自体の発火を止めきれないケースがあると判明。「ジェスチャーを止める」
  アプローチの限界と判断し、方針を転換。
- **対策**: 「ジェスチャーを止める」のではなく「ジェスチャーの結果として起きるアプリ内の
  戻る遷移そのものを無効化する」レイヤーとして`src/components/back-navigation-trap.tsx`
  を新規作成した。このアプリの画面遷移は全てLink/router.pushによる「進む」遷移のみで、
  どこからも`router.back()`/`history.back()`を呼んでいない(grepで確認済み)ため、
  観測される`popstate`イベントは全てスワイプ等による意図しない「戻る」とみなしてよい、
  という前提に基づく。具体的には(1)`usePathname()`で現在地を追跡し、遷移のたびに
  現在地の複製エントリを1つ`history.pushState`で積んでおく(戻る操作が来てもまず
  複製=同じ画面に着地する保険)、(2)`popstate`を検知するたびに`history.pushState`で
  現在地を積み直しつつ、Next.jsの描画も`router.replace(現在地)`で揃え直す、という
  2段構えにした。`EdgeSwipeGuard`(前回追加分)は残しつつ、`src/app/layout.tsx`の
  body直下に追加でマウントしている。
- 検証: `npx tsc --noEmit` / `npm run lint` はエラー無し。実際のブラウザ挙動(popstateの
  ハンドリング)はCSSやネイティブジェスチャーに依存せず検証可能なため、一時的に
  Playwrightを再導入し、開発サーバー(`npm run dev`)を起動した状態で、app router配下に
  一時テストページ2つ(`/swipetesta`⇄`/swipetestb`、Linkで相互遷移するだけの最小ページ)
  を作成して検証した。実ブラウザでA→B(Linkクリック)の後、`page.goBack()`(ブラウザの
  戻る操作=popstateを発生させる、実機のスワイプ戻ると同じ種類のイベント)を連続2回
  実行しても、両方ともURL・表示内容ともBに留まり続けることを確認(戻る遷移が実際に
  無効化されていることを裏取りできた)。
  **ハマった点**: 最初`__swipe_test_a`のようにアンダースコア始まりのフォルダ名で
  一時ページを作ったところ404になった。Next.js App
  Routerではアンダースコア始まりのフォルダは「プライベートフォルダ」としてルーティング
  対象外になる仕様のため、`swipetesta`/`swipetestb`のように普通の名前に変更して解決した。
  確認後、一時テストページ・一時スクリプトは削除、Playwrightはアンインストール
  (package-lock.jsonの差分も元に戻した)、開発サーバー(および子プロセス)も
  taskkillで停止済み。`.next/dev/types`配下に残っていた削除済みテストページの型
  キャッシュも削除し、`tsc`/`lint`が改めてクリーンであることを確認済み。
  実機での最終確認をユーザーに依頼する。
